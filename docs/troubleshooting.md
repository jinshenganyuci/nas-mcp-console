# 常见问题与排查

[返回首页](../README.md) · [部署指南](deployment.md) · [凭据配置](credentials.md) · [客户端接入](clients.md)

## 先区分哪一步失败

整个流程有三段：**客户端连接凭据库 → 读取获准访问的条目 → 客户端用凭据连接目标服务**。

网页能打开不代表 MCP Token 正确；MCP 能列出条目不代表目标 SSH 主机可达；GitHub 登录验证成功也不代表拥有删除仓库权限。按失败的那一段排查，通常不需要重新配置整个项目。

## 容器无法启动，或提示数据目录无写入权限

检查 Compose 的 `user` 与 `./data` 的实际所有者是否一致。默认是 `1000:1000`，Docker 自动创建的空目录可能归 root 所有。

```sh
id
ls -ldn ./data
docker compose -f compose.fnos.yaml ps
docker compose -f compose.fnos.yaml logs --tail=100 nas-mcp
```

让 `user` 与数据目录及其文件所有者匹配，再启动。不要用放开所有人写权限的方式解决。首次创建空目录与已有数据迁移的步骤见[部署指南](deployment.md)。

容器内部监听端口是 `8090`。修改 NAS 访问端口时只改映射左边，例如 `8793:8090`；不要同时改容器端口或健康检查地址。

## 找不到 first-login.txt，或者登录后文件消失

- 首次初始化在实际挂载的 `./data/first-login.txt` 创建临时密码。
- 修改管理密码成功后文件会自动删除，这是正常行为。
- 如果是刚部署的空库且没有文件，先检查容器是否成功启动，以及 `./data` 是否指向预期目录。
- 如果已有凭据而忘记管理密码，当前版本没有后台自助找回入口。不要通过删除 `state.json`、`master.key` 或整个数据目录尝试重置；这会破坏原库。保留完整备份后再排查。

## 更新后凭据全没了，又要求首次设置

优先检查挂载位置。`./data` 相对于 Compose 项目目录；把 Compose 文件搬到另一个目录、在飞牛新建另一个项目，或从命名卷改为 bind 挂载，可能让服务使用了新的空目录。

停止新容器，找到原目录或旧卷的完整数据，按[恢复与迁移说明](deployment.md)处理。不要把新旧库的文件混合；`vault.json` 必须配合同一份 `master.key` 使用。

## 外网域名返回 421：此访问域名尚未加入允许列表

先用 NAS 内网 IP 登录后台，在“设置访问入口”填写对外连接地址，例如 `https://vault.example.com:8794`。其域名会自动作为可信 Host；其他访问域名可加入“额外访问域名”（旧文案为“允许的 Host”），每行一个，不带协议、端口或路径。

**Host 是访问凭据库时 URL 中的域名或 IP，不是客户端的来源 IP。** 换电脑、换手机或换网络时，无需逐个登记客户端 IP。反向代理应保留原始 Host，包含使用的非标准端口。详见[访问入口](deployment.md)。

## MCP 返回 401：需要有效的 MCP 客户端凭证

检查客户端使用的是“客户端授权”中创建的 Token，而不是后台管理密码、GitHub PAT 或 Cloudflare Token。HTTP 请求头格式为 `Authorization: Bearer <客户端 Token>`。

同时检查以下情况：

- Token 是否被撤销、复制时是否缺字符、是否重复添加了 `Bearer`。
- 配置使用环境变量时，该变量是否对实际运行客户端的进程可见。终端里的 `export` 不会自动传给已运行的图形客户端。
- OAuth 授权是否超过 30 天、已被撤销，或对外连接地址发生变化；这些情况需要重新授权。
- 反向代理是否转发 `Authorization` 请求头，是否在 MCP 前额外加了客户端无法完成的网页登录。

手动 Token 只在创建时显示原文，后台无法找回。丢失后新建授权并替换客户端配置，再撤销旧授权。

## 浏览器打开 /mcp 报错，是否部署失败

`/mcp` 是协议接口，不是网页。普通浏览器 GET 不带凭据会得到 `401`；即使认证成功，本项目也不为 GET 或 DELETE 提供 MCP 事件流，返回 `405` 是预期行为。客户端应使用 **Streamable HTTP**，不要把它当作旧式 `/sse` 服务。

用浏览器打开 `/` 查看后台；基本存活检查使用 `/healthz`，例如在 NAS 上执行：

```sh
curl --fail http://127.0.0.1:8090/healthz
```

如果映射左边使用其他端口，修改命令中的端口。健康检查只证明服务可响应；完整 MCP 验证需要客户端完成初始化并调用 `list_credentials`。

## MCP 已连接，但看不到刚添加的凭据

`list_credentials` 只返回当前客户端授权范围内的条目。创建客户端时选择指定条目，以后新增的条目不会自动包含；选择“全部凭据”才包含未来新增项。

当前后台没有直接编辑已发出手动 Token 范围的界面。新建包含目标条目的客户端授权，替换客户端 Token，验证后撤销旧授权。OAuth 连接则重新发起授权并选择新的范围。

查询先使用空 `query` 查看获准访问的列表，再核对名称。`Credential unavailable` 也可能表示条目已删除、ID 拼写不匹配，或该授权无权读取；不要自行拼猜 ID。

## get_credentials 提示字段不可用

只使用 `list_credentials` 返回的 `available_fields`。例如 SSH 密码登录通常需要 `password`，私钥登录需要 `private_key`；Cloudflare Global API Key 的秘密字段是 `global_api_key`，API Token 的字段是 `token`。

未保存的可选字段不会出现在列表中。把密码登录条目同时请求成 `password` 和 `private_key` 会因后者不可用而失败。字段以实际列表为准。

## 新对话找不到 MCP，或仍反复索要密码

先确认连接保存到了客户端的持久配置，并且当前对话所在设备、用户或 profile 使用的是那份配置。安装或编辑连接后，按客户端要求刷新工具、重开对话或重启客户端。

再用一句明确的请求验证：

> 调用私人凭据库的 list_credentials，列出我可以使用的条目，只显示名称和类型。

如果能调用但不会主动使用，可把[客户端指南](clients.md)中的使用规则加入该客户端支持的持久指令。规则帮助模型选工具，不能替代 MCP 连接或授权。

Hermes 可先运行 `hermes mcp test private_credentials`。不同 profile 的配置相互独立，应在实际运行会话的 profile 中设置。Codex 的 GUI 进程是否能读到 Token 环境变量，也是常见原因。

## SSH 填了外网地址，为什么仍连接内网

默认入口仍是 `connection.host` / `port`。需要外网时，明确让客户端使用该条目的 `external_host` / `external_port`；两组地址共用登录凭据。未配置外网时，这两个可选字段不会出现。

「测试内网」只检查内网认证；公网 DNS、端口映射和防火墙需由实际外网客户端验证。保存外网字段不会自动建立映射、检测当前位置或切换连接。外网映射端口通常和内网 `22` 不同，应填实际对外端口。

## OAuth 页面无法添加、循环登录或回调失败

按顺序检查：

1. 后台已完成首次密码修改，并设置了正确的 HTTPS 对外地址；该地址不含 `/mcp`。
2. 客户端填写的是同一地址加 `/mcp`，身份验证选择 OAuth，保持自动发现与动态客户端注册。
3. 从真正发起连接的环境能访问该地址。云端连接通常不能直接访问你家的 `192.168.*` 内网地址。
4. HTTPS 证书受客户端信任，非标准端口也可达。代理转发完整路径、Host、查询参数、正文和认证头，不能只开放 `/mcp`。
5. 授权页、API、静态文件与发现端点都能访问，且响应没有被代理缓存。所需路径见[部署指南](deployment.md)。

未完成的授权页面有效期为 10 分钟；中途重启服务、页面过期或地址改变时，从客户端重新发起。已经完成的 OAuth 授权和刷新令牌会持久化，但授权撤销、30 天到期或改变对外地址仍需重新授权。

具体客户端必须支持本服务的 OAuth 流程。是否开放自定义 MCP 添加入口取决于客户端版本、账号和管理员设置，不能靠更改凭据库设置启用一个不存在的客户端功能。

## 测试凭据成功，实际操作却没有权限

后台测试验证的是有限的认证过程，未执行删除仓库、推送镜像或改 DNS 等操作。请同时检查：

- 上游 Token 的权限、资源范围和有效期。
- Token 所属账号是否本来就有目标仓库、组织、域名或命名空间权限。
- 客户端是否具备所需工具，是否能访问目标网络。

不同类型的测试范围和 Token 获取步骤见[凭据配置指南](credentials.md)。

Cloudflare 有一个特别情况：当前 API Token 测试使用用户级 `/user/tokens/verify`。账户级 API Token 可能在此验证失败但仍能调用被授权的业务接口；不能仅凭这个结果断定账户级 Token 无效。

## SSH 首次要求确认指纹，或指纹发生变化

后台先取得 SSH 主机公钥指纹，确认后才发送登录凭据。通过服务器控制台或已信任的连接核对指纹。

重装服务器或更换 SSH 主机密钥可能导致指纹变化。当前后台没有原地重置信任按钮；已有信任记录与新公钥不符时，会直接拒绝登录。核实新主机身份后，用新名称创建 SSH 条目，重新核对指纹并测试，再更新客户端授权；确认可用后删除旧条目。不要通过忽略主机密钥校验掩盖连错主机的问题。

## latest 已拉取，为什么看起来没更新

确认 Compose 的 `image` 末尾实际使用的是 `:latest`。默认发布 Compose 固定为 `:0.4.0`，拉取固定标签不会自动改成未来版本。

拉取之后还需要 `docker compose -f compose.fnos.yaml up -d`，让容器使用新镜像。保持原有项目目录、挂载路径和运行 UID/GID 不变；更新前先完整备份数据。

## 反馈问题时需要什么

提供镜像标签、CPU 架构、部署方式、具体失败步骤，以及脱敏后的错误或状态码。与客户端有关时补充客户端名称、版本及 Token / OAuth 连接方式。

不要上传 `data`、`.env`、管理密码、Token、完整认证请求头或包含秘密的工具返回。日志和截图也应先去掉这些内容。可通过仓库的 [Issues](https://github.com/jinshenganyuci/nas-mcp-console/issues) 反馈可公开复现的问题。
